## 🆕 本次新发现：gold 重放的 4 道失败题，机制完全确定

**这是本次补全的地基，所以放最前面。**

### 事实

`tau-bench/tau_bench/envs/base.py:125-165` 的 `calculate_reward` 有**两段独立判定**：

```python
# 第一段：数据库状态哈希比对（一直生效）
data_hash = self.get_data_hash()
for action in self.task.actions:
    if action.name not in self.terminate_tools:
        self.step(action)
gt_data_hash = self.get_data_hash()
if data_hash != gt_data_hash:
    reward = 0.0

# 第二段：outputs 检查（只有 task.outputs 非空时才生效）★
if len(self.task.outputs) > 0:
    for output in self.task.outputs:
        found = any(
            action.name == RESPOND_ACTION_NAME
            and output.lower() in action.kwargs["content"].lower().replace(",", "")
            for action in self.actions
        )
        if not found:
            reward = 0.0
```

**关键**：`respond` 的内容**会被检查**，但只对 `task.outputs` 非空的题；判定方式是**大小写不敏感、剥掉逗号后的子串包含**。

### 与实测的一一对应

| | |
|---|---|
| airline 50 题中 `outputs` 非空的 | **4 道**：`task[2] ["23553"]` / `task[8] ["327","1000","1786"]` / `task[9] ["327","1000","1286"]` / `task[44] ["4"]` |
| `A_replay`（gold 重放，无 respond）的 0 分位置 | **index 2, 8, 9, 44** |
| 重合度 | **4/4，完全一致** |
| `B_replay_respond`（补了合成 respond） | **50/50 全 1.0** |

### 这条事实的三个含义

1. **`A = 46/50` 不是随机噪声，是一个可解释的机制**。README 里"重放+合成 respond = 50/50"的写法掩盖了因果——准确说法是：**补 respond 恰好补上了这 4 道题的 outputs 检查**。
2. **SFT 的收尾回复不是"随便合成一句话"**，其中有一层是**硬约束**（见洞 2）。
3. **`outputs` 是一个可用的实验旋钮**——它能把"无区分度题"改造成"有区分度题"（见洞 1）。

### 待验证

- [ ] 在 `env/` 里跑一个探针，确认「给一道无写动作的题手动加上 `outputs` 后，no-op 策略的 reward 从 1.0 掉到 0.0」
- [ ] 确认扩题器生成的题能否挂 `outputs`（`Task` 是 pydantic 模型，`outputs: List[str]` 是必填字段，构造时应无阻力）

## 洞 1 ｜ 20 道无区分度题怎么处理（README 标"最高优先级"）

### 问题回顾

| 测量（v3 实测） | 结果 |
|---|---|
| gold 重放后数据库**没变**的题 | 20 / 50（40%） |
| 其中：gold 里**一条写动作都没有** | 16 道（含 7 道 0 动作题） |
| 其中：只有 `transfer_to_human_agents`（在 `terminate_tools` 里，重放被跳过） | 4 道 |
| "什么都不做"直接拿 1.0 的题 | **19 / 50（38%）** |

**为什么致命**：reward 与策略行为无关、恒为 1.0。进 GRPO 组内归一化 → 全组不动则 `std=0` 零梯度；一旦组内有方差，梯度指向**「别调工具」**——**等于人为制造出我们要研究的"欠调用"现象**。

### 方案：**训练和评测分开处理，而且不丢弃**

核心判断：**这 20 道题在训练里是毒药，在评测里是资产。**

#### 1-A 训练集：剔除，但只剔"毒"的那部分

**不是 20 道全剔。** 按"策略乱调工具会不会被惩罚"重新分：

| 子类 | 题数 | 乱调工具会怎样 | 处理 |
|---|---|---|---|
| gold 0 写动作 + **无 outputs** | 16 | DB 被改 → 哈希不等 → **reward 掉到 0** | ⚠️ **其实有区分度！** 见下 |
| gold 只有 `transfer_to_human_agents` | 4 | 同上 | 同上 |

**这里要纠正 v3 报告的一个措辞**：报告说"reward 与策略行为无关、恒为 1.0"，严格讲**只对"什么都不做"这个策略成立**。
一个**会乱调工具**的策略在这 20 道题上照样拿 0 分。

> ⭐ **准确表述**：这 20 道题的 reward **区分不了"好"和"什么都不做"，但能区分"什么都不做"和"乱调"**。
> 也就是说它们**不是零信号，是单边信号**——只惩罚过调用，不奖励任何正确行为。

**这直接改变处理方式**：

- **对 GRPO 组内归一化的危害依然存在**：如果一组 8 条采样全部"什么都不做"，`std=0`；而 SFT 预热后的 1.5B 大概率**全都不会调工具**（见 Stage 1 判据）→ **整组零方差是常态而非例外**。
- **所以训练集处理 = 剔除**，但**要记录下来**，因为剔除的理由是"单边信号在弱策略下退化为零信号"，不是"这题没意义"。

**判据**：训练集 = 30 道（有真写动作的），且**每道都必须通过一条检查**——「gold 里至少有一条写动作」。
**待验证**：跑一个脚本，确认 30 道题在 SFT 前模型上的 pass rate 不是 0（否则 Stage 1 判据要下调难度档）。

#### 1-B 评测集：**全部保留，单独成组，作为"过调用"的专用探针** ⭐

这是这条设计的价值所在。

这 20 道题精确地测量一件事：**模型会不会没事找事乱调工具**。

| 指标 | 定义 | 诊断 |
|---|---|---|
| **过调用率** | 在这 20 道题上，模型是否执行了**任何**写动作 | 工具使用退化谱 · **过调用** |
| 空转轮数 | 无写动作题上的平均 assistant 轮数 | 啰嗦 / 无效搜索 |
| 误报伤害 | 因乱调导致 DB 变化的题数占比 | 真实损害 |

**为什么这比"删掉"好一万倍**：

- longhorizon 的三大病因**不含工具使用行为**——它 14 个工具白摆着。
- 我们要做的"工具退化谱"里，**"过调用"这一维在 50 题上天然只有这 20 道能测**。
- 删掉 = 亲手把唯一的过调用探针扔了。

**而且它是"零成本"的**：这 20 道题的 gold 已经验证过、env 已经跑通，只是换个用法。

#### 1-C 可选增强：用 `outputs` 机制把单边信号补成双边信号

**如果**训练数据量不够（30 道对 GRPO 偏少），可以**改造其中一部分**，而不是丢弃：

给一道"gold 无写动作"的题**手动加上 `outputs`**，让 reward 变成：

```
原始：改对了 DB（不做就对了）= 1.0          ← 单边
改造：改对了 DB + respond 里汇报了关键信息 = 1.0  ← 双边
```

一个"什么都不做"的策略**不会产生 respond** → outputs 找不到 → **reward 掉到 0**。区分度立刻出现，**而且用的是 τ-bench 原生机制，一行 reward 代码都不用改**。

**改造后测的是什么能力**：**把查到的信息汇报给用户**——这是客服场景里最真实、也最容易被 RL 训丢的能力。

⚠️ **风险**：这是**改数据**，不是改环境。改造后的题与原 benchmark 不可比，**必须单独标记**，报告里也要区分"原生 30 题"和"改造 N 题"的结果。
⚠️ **不要改造全部**——全改了就没有"过调用探针"了，1-B 的价值被抵消。

**判据**：改造题的 no-op 策略 reward **必须 = 0.0**（探针验证）。
**建议配比**：改造 **≤ 8 道**，保留 **≥ 12 道** 原样作探针。

### 待验证清单

- [ ] 脚本确认：20 道题里，"什么都不做"得 1.0 的是 **19** 道（v3 已有数字），差的那 1 道是哪道、为什么
- [ ] 探针：手动给 1 道题加 `outputs` → no-op 的 reward 从 1.0 → 0.0
- [ ] 训练集 30 道 + 评测探针 20 道的**清单文件**落到 `data/`（JSON，可复现）
- [ ] 决定改造几道（建议 ≤ 8）

## 洞 2 ｜ SFT 的收尾回复怎么补（v3 标"可行路径待定"）

### 问题回顾

v3 实测发现：**gold action 序列里 `respond` 出现 0 次** → 重放出来的轨迹没有收尾回复 → 直接当 SFT 数据不可训练。

### 方案：**分两层，一层是硬约束，一层是自由的**

基于本次新发现，"合成收尾回复"**不是一个问题，是两个**：

#### 层 1（硬约束）｜有 `outputs` 的题：respond **必须包含 output 字符串**

- **题数**：原 50 题里 4 道（8%）；扩题后按扩题器规则重算
- **判定**：`output.lower() in respond_content.lower().replace(",", "")`
- **合成方式**：**模板即可，不需要 LLM**。把 outputs 嵌进一句话：

```
"我已经为您处理完成。您需要的信息是：23553。"
"已完成您的请求。相关信息：327、1000、1786。"
```

- ⚠️ **不能漏、不能改数字、不能加逗号以外的干扰**。逗号会被剥掉，所以 `1,000` 和 `1000` 等价；但拼错一位就判定失败。
- ⚠️ **这是 reward 判定的一部分，不是"措辞好不好"的问题** → 这一层的文本**必须由程序生成，不能让 LLM 自由发挥**。

#### 层 2（自由）｜无 `outputs` 的题：respond 内容**不进 reward**

- **题数**：原 50 题里 46 道（92%）
- **含义**：写什么都不会影响正确性判定
- **但**：**不能省**。原因：
  1. τ-bench 的 episode 需要终止动作，SFT 数据必须教模型**什么时候停**
  2. 省掉收尾 → 模型学到"永远不停" → rollout 撞上 max_turns 被截断 → 拿 0 奖励 → 又变成"没信号"

**层 2 的三个合成来源（按推荐顺序）**：

| 方案 | 做法 | 成本 | 文本真实性 |
|---|---|---|---|
| **① 模板** | `"我已为您完成：{动作序列的自然语言化}"` | 0 | 低（但 reward 不看，够用） |
| **② 从 268 条真实轨迹挖** | `historical_trajectories` 里 gpt-4o/sonnet 的成功轨迹，取它们的收尾 assistant 轮当模板库 | 0（本地已有） | **高**（真实分布） |
| **③ LLM 生成** | DeepSeek 按 (instruction + 动作序列 + 终态) 生成收尾 | 每题 1 次调用 | 高 |

**推荐组合：① + ②**。
- 模板保证 100% 正确、可复现、零成本
- 从 268 条真实轨迹挖来的句子做模板池，避免所有轨迹结尾一模一样（**同类文本全同会让模型学到无信息量的固定串**）
- ③ 留作"如果要更自然"的增强，**但引入 API 就把"零成本无限量"的优势打掉了**，所以不作默认

### ⚠️ 三个必须写死的约束

1. **层 1 的 respond 必须是程序拼的**，LLM 生成的一律不用（怕它改数字）
2. **层 1 和层 2 要分别统计**，报告里写清"SFT 数据 N 条，其中 M 条带硬约束收尾"
3. **不能只合成收尾**：中间那些"工具调用之间的 assistant 文本"（reasoning）gold 里也没有，同样要补。
   - 这一层**没有 reward 约束**，纯风格 → 可以用模板 / 短句 / 直接空
   - ⚠️ 但如果全空，模型学到的是"不推理直接调工具"→ 与 longhorizon 报告的"reasoning p50 63 → 22 token 模式压缩"是**同一个退化**，而且是我们**自己喂出来的**
   - **建议**：这一层也要有内容。从 268 条真实轨迹挖 reasoning 片段作模板池

### 待验证清单

- [ ] 统计：gold action 序列里 `respond` 确实 0 次（v3 已验，复现一次）
- [ ] 统计：gold 里"动作之间的 assistant 文本"是否也缺失 / 缺失比例
- [ ] 从 `historical_trajectories` 抽出：268 条成功轨迹的收尾轮 + 中间 reasoning 轮，做成模板池 → `data/respond_templates.json`
- [ ] 合成 1 条完整轨迹，**丢回 `env` 重放，确认 reward = 1.0**（这是层 1 的硬判据）

## 洞 3 ｜ 扩题器设计

### 问题

README 说"采样 (user, reservation) → 模板化 instruction + gold action → 500–2000 个难度分级任务"，但没说怎么采样、怎么保证 gold 正确。

### 方案

#### 3-A 三条难度档的生成规则

| 档 | 生成方式 | gold 动作数 | 用途 |
|---|---|---|---|
| **easy** | 单实体单动作：改一个已有订单的行李额 / 查一个用户的信息 | 1–2 | Stage 1 兜底（SFT 后 pass@1 < 5% 时降级到这里） |
| **medium** | 多实体 2–3 动作：改航班 + 改座位 + 汇报 | 2–4 | **Stage 2 主训练档** |
| **hard** | 需要先查询才能知道改什么（信息依赖链）：先查订单 → 从结果里拿 ID → 再改 | 4+ | Stage 3 课程重标定 |

#### 3-B 生成流程（关键：**gold 必须由环境验证过，不能靠模板猜**）

```
① 从 users.json / reservations.json 采样一个 (user, reservation) 组合
        ↓
② 按难度档套模板，生成 instruction 草稿 + 候选 action 序列
        ↓
③ ⭐ 在 env 里真实执行候选 action 序列：
       - 能跑通（不报错）→ 保留
       - DB 哈希确实变了 → 保留（这是"有区分度"的必要条件）
       - 任何一步失败 → 丢弃
        ↓
④ 对保留下来的题，判定是否挂 outputs（见 3-C）
        ↓
⑤ 写入 tasks 文件，格式与 tasks.py 完全一致
```

**③ 是这一步和"模板化生成"的本质区别**：**扩题器的产出必须经过 oracle 验证**，就像原 50 题一样。README 里"零成本无限量"的成立前提是"生成 → 验证 → 只留通过的"，不是"生成即用"。

#### 3-C ⭐ `outputs` 字段的分配规则（这是扩题器最容易漏的地方）

**为什么关键**：原 50 题里只有 4 道（8%）有 outputs。如果扩题器**不生成 outputs**，那么：

- 扩出来的几百道题**全部属于"层 2"**（收尾内容不进 reward）
- 模型**学不会"主动汇报关键信息"**——而这恰恰是客服场景最核心的能力
- 更糟：**扩题把 outputs 题的占比从 8% 稀释到接近 0%**，等于自己制造了一个能力盲区

**分配规则**（建议）：

| 难度档 | outputs 比例 | 理由 |
|---|---|---|
| easy | ~10% | 与原 50 题一致 |
| medium | **~25%** | 主训练档，要保证"汇报"能力被充分训练 |
| hard | **~40%** | 多跳任务天然需要汇报中间结果 |

**每道挂 outputs 的题，output 串必须是"动作执行后才知道的值"**（订单号、金额、座位号），不能是 instruction 里已经给过的。

#### 3-D 与 longhorizon 的对照（这是叙事核心）

| | longhorizon | 扩题器 |
|---|---|---|
| 造题方式 | 72B 模型 best-of-16 采样，**7.2 小时** | 程序化 + env 验证 |
| 训练集 | **40 条** | **400+** |
| 泛化指标 | **10 道 unseen** | **200+ 真不相交** |

**叙事**：*它说"加数据不是可选解法"，我证明了那是它数据构造方法的限制，不是问题本身。*

### 待验证清单

- [ ] 采样可用性：`users.json` / `reservations.json` 里能组合出多少个不重复的 (user, reservation)？**这决定扩题器的天花板**
- [ ] 跑通 1 道手写 medium 题：模板 → env 执行 → 哈希变化 → 通过
- [ ] 确认 `Task` 是 pydantic 模型，构造新题时 `outputs` 字段能正常写入
- [ ] **难度分档的判据**：easy/medium/hard 的定义要落成可执行的规则，不能靠感觉

## 洞 4 ｜ 规则模拟器 slot 版

### 问题

`env/user_sim.py` 当前是**占位版**。README 的设计是：

> `tasks.py` 的 instruction 用**一次性 DeepSeek 调用**解析成 slot dict 缓存 JSON；运行时关键词匹配返回 slot；匹配不到返回固定兜底句。

### 方案

#### 4-A 三档降级链（README 已写，这里补判据）

```
档 1  规则式（slot 解析）    ← 目标
档 2  回放式（268 条真实轨迹的 user 轮）
档 3  easy 档任务（instruction 更短、信息更直白）
```

#### 4-B 档 1 的实现要点

**离线阶段（一次性）**：
```
对每道题的 instruction 调一次 DeepSeek：
  输入：instruction 原文
  输出：{"user_id": "...", "name": "...", "confirmation": "...", "flights": [...], "reason": "..."}
存成 data/user_slots.json（50 条 → 扩题后 N 条）
```

**在线阶段（每轮）**：
```
agent 说了一句话
    ↓
关键词匹配：从句子里的实体（订单号 / 人名 / 航班号）反查 slot
    ↓
命中 → 返回对应 slot 值
未命中 → 返回兜底句（"不好意思，您说的是什么意思？"）
```

#### 4-C ⚠️ 三个设计约束

1. **确定性**：固定匹配顺序 + 固定兜底句，**同一个输入必须给同一个输出**。规则模拟器引入随机 = 把 longhorizon 的 eval 噪声问题请回来。
2. **必须能复现**：slot 解析结果**存盘**（`data/user_slots.json`），不在运行时调 API。这样离线可复现、也不吃 token。
3. **"匹配不到"要计数**：兜底句的触发率是**模拟器质量的直接指标**。如果触发率 > 30%，说明 slot 抽得不够，模拟器会退化成"复读机"，模型学到的是"跟复读机说话"。

### 为什么这不只是工程妥协（README 已指出，这里补量化）

longhorizon 自己的诊断文档写"**user simulator 是 eval 噪声的主要来源**"。换规则模拟器后：

| | longhorizon | 我们 |
|---|---|---|
| reward 方差来源 | policy + LLM 模拟器（**混杂**） | **100% 来自 policy** |
| 归因链 | 分不清是模型坏了还是模拟器飘了 | 干净 |

**这直接支撑项目核心命题**：要研究"坍塌≠没信号"，前提是**信号的噪声源可控**。

### 待验证清单

- [ ] 跑一次全 50 题的 slot 解析，人工抽检 10 条
- [ ] 统计兜底句触发率（判据：< 30%）
- [ ] 确认同一输入多次调用结果一致（确定性测试）

## 洞 5 ｜ 观测器 + 评测 harness

### 问题

`observe/` 目录整个是空的。README 说要做"四指标观测器 + 工具退化指标"，但没定义。

### 5-A 观测器：两类指标，**必须分开**

#### 类 1：训练健康度（每个 step 记，判"有没有信号"）

| 指标 | 定义 | 判据 |
|---|---|---|
| **组内零方差率** ⭐ | 一个 group 内 8 条 rollout reward 全同的比例 | **> 80% → 题太难，没信号**（README R1 的第一监控指标） |
| reward 均值 / 方差 | | |
| episode 长度分布 | token 数 p50 / p90 | 对照 2512 / 4009 |
| assistic 轮数 | avg_turns | 对照 longhorizon 7.3 → 5.08（坍塌时的行为） |
| KL(base ‖ policy) | 用 LoRA adapter 开关算，不加载第二个模型 | |
| 熵 | 生成分布的熵 | 熵坍塌 |

#### 类 2：工具使用退化谱 ⭐（本项目的核心创新，每个 checkpoint 记）

| 退化模式 | 操作性定义 | 探针 |
|---|---|---|
| **欠调用** | 该调工具的任务上，assistant 轮里工具调用数 = 0 的比例 | 30 道"有写动作"的题 |
| **过调用** | 不该调工具的任务上，执行了**任何**写动作的比例 | **洞 1-B 的 20 道探针题** |
| **抖动** | 同一工具被反复调用的次数 / 不同工具数的比 | 全量 |
| **空转** | 无写动作题上的 assistant 轮数 | 20 道探针题 |

**⭐ 这是"补上 longhorizon 没看的第四维"的具体落地。** 它的三大病因（group reward 饱和 / 训练集泄漏 / 长推理能力下降）**都不含工具使用行为**。

### 5-B 评测 harness

**口径**（抄 longhorizon 的 pass@k）：

```
N = 4 采样
区分三类任务：
  covered    train 里出现过
  uncovered  train 里没出现、但同分布
  unseen     train/eval 真正不相交
```

**为什么这套口径重要**：longhorizon 的 `train ∩ eval = 40/50 = 80%` 重合，它的"泛化"指标只有 10 道 unseen 题，**统计上不可靠**。扩题后我们的 unseen 能到 200+。

**输出**：一个 `eval.py`，给定 checkpoint 目录 → 输出 Markdown 表格：
- pass@1（covered / uncovered / unseen 分列）
- **组内零方差率**
- **四条退化曲线**
- avg_turns / 长度分布

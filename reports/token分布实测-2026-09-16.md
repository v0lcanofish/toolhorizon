# 二、⚠️ 修正 9/15 的显存账

## 9/15 写的是

> "实测轨迹长度（gpt-4o-airline 成功轨迹）：p50 ≈ **2,512** token ｜ p90 ≈ 4,009 ｜ max ≈ 4,464"
> "它标称 16K，**真实成功轨迹中位数只有 2.5K** → 显存需求比标称小一个量级"

## 实测发现

**2,512 ≈ 我这边 gpt-4o 的 2,624（不含 schema）** —— 9/15 的测量**漏算了工具 schema**。

```
工具 schema 的固定开销（Qwen2.5 tokenizer 实测）：
  14 个工具：9,172 字符 → 3,249 token
  12 个工具：8,585 字符 → 3,062 token
```

**这是每一轮都要带的固定税**，漏了它，轨迹长度被低估 2.2–2.8 倍。

## 正确结论

> ✅ **真实成功轨迹 p50 = 6,692 token**（含 schema），**不是 2,512**。
> 标称 S_max=8192 与实测中位数是**同一量级**（1.2×），**不是"小一个量级"**。
> ⚠️ 而且 **p90 = 10,287 > S_max 8192** → **必须做截断策略**。

## 对显存账的影响

| | 按标称 8192 | 按实测 p90 10,287 |
|---|---:|---:|
| logits 单张量 | 8192 × 151,643 × 4B = **4.97 GB** | **6.24 GB** |

**✅ 结论不变：fused/chunked CE 仍是必须的**（单个 logits 张量就 5–6 GB）。
但 **S_max 需要重新决策**：8192 会截掉 p90 的轨迹。

# 三、⭐ 一个新发现：tool 结果占了 65.7%

单条 24 消息轨迹的 token 构成：

| role | 条数 | token | 占比 |
|---|---:|---:|---:|
| **tool（工具返回）** | 6 | 3,574 | **65.7%** |
| system | 1 | 1,265 | 23.2% |
| **assistant（唯一被训练的）** | 11 | 492 | **9.0%** |
| user | 6 | 112 | 2.1% |

**两个直接后果**：

1. ⭐ **assistant token 只占 ~12%** —— 印证了 README 的判断
   "轨迹只有 ~10% 是 assistant token，不做 mask-only logits 就是 10 倍浪费"。
   **`logits_to_keep` 不是优化，是必需。**

2. ⭐ **工具返回是最大的一块（65.7%）** —— 而且大部分是无用字段（完整航班列表 JSON）。
   **裁剪 tool 返回的字段可以砍掉大量 token**，这比调 S_max 更划算。

### 2.2 两个语义纠正

**纠正 A：`task.actions` 不含最终回复。**
50 题的 gold 里 `respond` 出现 **0 次**，但有 4 道题带 `outputs`（要求最终回复里必须出现的字符串）。
→ 「重放 gold 得到 SFT 数据」**不成立**，重放出来的轨迹没有收尾答复。

**纠正 B（推翻了本目录脚本的早期版本）：`task.actions` 不是「只记录落库变更」。**
62% 是只读动作（`get_*` / `search_*` / `calculate`）。
→ 它是**读写混合的参考动作序列**，只缺「搜索规划」和「最终回复」两段。

**正确表述**：`task.actions` = *该任务必须发生的动作序列（不含自由文本交互）*，
其中只有写动作会影响奖励。

## 三、⭐ 核心发现：40% 的题没有区分度

### 3.1 测法

对每道题：
1. 新 env → `reset` → 记下数据库哈希 `h_fresh`
2. 重放 gold 动作 → 再记哈希 `h_after`
3. 若 `h_fresh == h_after`，说明**这道题的 gold 根本改不动数据库**

再单独测「什么都不做，直接结算」的 reward。

### 3.2 结果

| 测量 | 结果 |
|---|---|
| A. gold 重放 | **46 / 50** |
| B. gold 重放 + 合成 respond | **50 / 50** ✅ |
| C. **什么都不做** | **19 / 50（38%）** |
| 重放 gold 后数据库**没变**的题 | **20 / 50（40%）** |

A 挂掉的 4 道，正是仅有的 4 道带 `outputs` 的题（task 2 / 8 / 9 / 44）——
只重放动作、不回复，`r_outputs` 判 0。B 补上合成回复后全通过。
**→ 这反过来证明 reward 的三个分支（哈希 / outputs / 终止工具）都被激活过，测量可信。**

C 的 19 与「DB 没变」的 20 差 1 道（task[44]）：它虽然 DB 中性，但被自己的 `outputs` 挡住了。

### 3.3 这 20 道题是什么

| 类型 | 题数 | 说明 |
|---|---:|---|
| gold 里**一条写动作都没有**（含 0 动作题 7 道） | **16** | 只读动作改不动数据库，可以理解 |
| gold 只有 `transfer_to_human_agents` | **4** | 该工具在 `terminate_tools` 里，`calculate_reward` **重放时会跳过它**（`base.py:136`），且它本身不改数据 |

**交叉表（写动作数 → 有无区分度）**：

```
写动作 0 条：有区分度  0 题 | 无区分度 16 题
写动作 1 条：有区分度 15 题 | 无区分度  4 题   ← 全是 transfer_to_human_agents
写动作 2 条：有区分度  8 题 | 无区分度  0 题
写动作 3 条：有区分度  4 题 | 无区分度  0 题
写动作 4 条：有区分度  2 题 | 无区分度  0 题
写动作 5 条：有区分度  1 题 | 无区分度  0 题
```

**只要 gold 里有一条真正的写动作，题目就有区分度。** 规律非常干净。

### 3.4 为什么这是致命的（对 GRPO 而言）

对这 20 道题：**奖励与策略行为无关，恒为 1.0。**

放进 GRPO 的组内归一化 `A_i = (r_i - mean) / (std + eps)`：

- 若组内 8 条 rollout 全部什么都不做 → `std = 0` → **advantage 全 0，这一步零梯度白跑**
- 若组内有方差（有的调了工具、有的没调）→ 梯度方向指向**「别调工具」**因为调了反而改坏数据库拿 0

> ⚠️ **这等于人为制造出我们要研究的「欠调用（学会猜）」现象。**
> 它不是模型自己学坏的，是**数据喂出来的**。

**这条直接把项目的核心命题从「设想」变成「有实测支撑」**：
项目说「不是坍塌了所以没信号，是没信号所以表现得像坍塌」——
现在拿到了数据侧的确凿证据：**参考数据集里 40% 的题天生零信号**。

而且这条是 **longhorizon 没报告的**。它自己承认「τ-bench airline 官方只有 50 个 task，
数据量小是本项目最核心的结构性约束」——**但实际可用的只有 30 道**。

## 四、工具子集的正确方案（推翻 README 的 14→7）

### 4.1 一个反直觉的实测结果

`verify_oracle.py` D 组：**砍掉 `cancel_reservation`（11 道题在用）之后，
gold 重放的通过率一点没降，仍是 46/50。**

原因：`calculate_reward` 不是拿 agent 的结果去比对「标准终态」，
而是**用同一套 `tools_map` 把 gold 重放一遍**再比哈希。
工具被砍 → agent 调它失败，gold 重放它也失败 → **两边同样 no-op，哈希照样相等**。

> **所以砍工具的代价不是「reward 归零」，而是「题目失去区分度」。**
> （本目录脚本的早期版本推断「reward 恒为 0」，是错的，已回写修正。）

### 4.2 各方案实测对比

| 方案 | 工具数 | 有区分度 | noop 满分 | 废题率 |
|---|---:|---:|---:|---:|
| 全量（基准） | 14 | **30** | 19 | 40% |
| 砍 `think` + `list_all_airports` | 12 | **30** | 19 | 40% |
| 只保留 gold 出现过的 | 11 | **30** | 19 | 40% |
| **README 的 14→7 方案** | 7 | **14** | 33 | **72%** ⚠️ |

README 方案**额外废掉 16 道题**：`[0, 1, 8, 9, 10, 11, 16, 25, 27, 28, 30, 31, 32, 43, 45, 46]`。

### 4.3 修正后的决定

**采用 12 个工具**（14 − `think` − `list_all_airports`），零区分度损失。
`search_onestop_flight` 虽然 gold 里 0 次、砍了也不掉区分度，但 **agent 真的需要它**
（task[0] 的 instruction 明写 "one stopover also fine"）——
**gold 不记录搜索类动作 ≠ 搜索不需要发生**，所以保留。

`think`（返回空串）和 `list_all_airports`（wiki 里已有）无叙事价值，砍掉。

### 4.4 token 账（README 数字修正）

| | 字符 | ≈token |
|---|---:|---:|
| 14 个工具 schema 合计 | 9,144 | 2,345 |
| 12 个 | 8,561 | 2,195 |
| 11 个 | 7,979 | 2,046 |

README 写的是「≈13,528 字符 ≈ 3,400 token」——**高估了约 48%**。
真实值 2,345 token，对 8K context 是 29% 固定税（不是 40%）。
